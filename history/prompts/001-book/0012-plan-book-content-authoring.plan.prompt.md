## Prompt

Phase 3, Step 4: create the plan and tasks for the book content (feature:
001-book). We already have the spec, the chapter-authoring skill, and the
three subagents. Now produce the technical plan and the task breakdown.

## Part 1 — /sp.plan
Run the planning step for specs/001-book/spec.md. The plan should cover:
- Folder structure under book/docs/ for 4 modules + chapters (module folders,
  _category_.json for module order, chapter files with sidebar_position).
- The introduction page replacing the current placeholder intro.mdx.
- Module landing pages.
- The authoring workflow: chapter-writer drafts using the chapter-authoring
  skill, then code-verifier and consistency-checker review independently, then
  fixes are applied — per chapter.
- How the ROS-code execution gap is handled (this machine has no ROS 2; some
  examples can't be run here — the plan must state how those are marked).
- Build verification after each module (npm run build must stay green).
- Respect the constitution and the confirmed Jazzy/Harmonic/Ubuntu 24.04 target.

## Part 2 — /sp.tasks
Break the plan into tasks. Expected shape:
- One task per chapter (14 total), each including: write with skill, verify
  code, check consistency, apply fixes.
- Tasks for the 4 module landing pages and the introduction page.
- Tasks for _category_.json files and sidebar ordering.
- A build-check task after each module.
- Order tasks so Module 1 ships complete before Module 2 starts (per the
  spec's user-story priority).

## Constraints
- Do NOT write any chapter content yet — plan and tasks only.
- Keep tasks small and independently checkable.
- After both, summarize the plan approach and list the tasks in order.

## Summary at end
- The plan's key decisions
- The full ordered task list
- What the first chapter task will involve

*(This PHR covers Part 1. Part 2 is recorded in PHR 0013.)*

## Response snapshot

Ran `setup-plan.ps1` with `SPECIFY_FEATURE=001-book` (the session is on `main`, and
`Get-CurrentBranch` checks that variable before git). Produced five artifacts.

**plan.md** — seven key decisions:

- **D1** Module landing pages are `index.mdx` inside the module folder, using Docusaurus's category
  index convention. `_category_.json` carries only `label` and `position`.
- **D2** Ordering declared at two levels — `position` for modules, `sidebar_position` for chapters,
  landing page always 1. No numeric filename prefixes, satisfying Principle V.
- **D3** `intro.mdx` rewritten in place, keeping `slug: /` and `sidebar_position: 1`.
- **D4** Per-chapter pipeline: draft → both reviewers in parallel → fix → re-review if a blocker
  was fixed.
- **D5** The execution gap, below.
- **D6** `npm run build` after every module, plus a baseline run before any content change.
- **D7** Sequencing by spec user-story priority; chapters in catalog order within a module.

**The execution gap (D5)** is the plan's substantive decision. This machine is Windows with no
ROS 2, Gazebo, or Isaac, and Principle II requires execution before a chapter is done. Rather than
let that be resolved silently, "done" is split into `drafted` and `verified`, with per-example
status in `specs/001-book/verification-log.md`. The marker is repo-side, never reader-facing; a
chapter never asserts an output nobody observed; and no chapter is reported done while any example
is `pending-env`. Recorded as the single entry in **Complexity Tracking** with both simpler
alternatives and why each was rejected.

**Constitution Check**: five principles pass; Principle II is marked **conditional** rather than
passing, because claiming otherwise would be false.

**research.md** — R1 category index convention (verified, not assumed), R2 execution environment
options with `osrf/ros:jazzy-desktop` on WSL2 chosen, R3 Isaac ROS `release-4.5` line with
re-confirmation deferred to Module 3 start, R4 `trailingSlash` recommendation, R5 MDX over MD.
Three items are carried forward explicitly as unresolved, with the owner decision each needs.

**data-model.md** — the content structure as entities (Book, Introduction, Module, Chapter,
Learning objective, Code example, Exercise, Verification log entry, Review finding), with the
Chapter state machine `absent → drafted → verified`.

**contracts/chapter-file-contract.md** — this feature has no API, so the contract is the file on
disk: path and naming, frontmatter schema per file type, section order, code-block requirements
including the prohibited Lyrical `rclpy` forms, linking rules, prohibited content, and an
11-item acceptance checklist. It is also what the later `002-chatbot` ingestion will parse.

**quickstart.md** — the six-step authoring loop plus six rules that are easy to get wrong.

Two claims were verified against official Docusaurus documentation before being written into the
plan rather than after: the category index convention (`index` / `README` / folder-name, and the
caveat that `position` orders only within a sidebar slice), and `trailingSlash` semantics.

`update-agent-context.ps1 -AgentType claude` ran successfully; `git diff CLAUDE.md` came back
empty, so no unintended change to project instructions.

No chapter content written.
